## 1. What we are building
Telos is NOT primarily a web framework, AI framework, graph database, or workflow engine. **Telos is a semantic-first programming system for agent-native software engineering.** It makes software meaning, structure, dependencies, constraints and available operations accessible through executable programming interfaces. Instead of agents reconstructing architecture by reading files/grepping/guessing, software built with Telos exposes its own semantic structure and capabilities. The software is the authoritative source of information about its intended organization.

Three levels:
- **L1 Semantic Programming**: all managed code belongs to an explicit semantic context. Semantic identity and ownership; universal Locus model; composable semantic extensions; typed semantic relationships; semantic introspection; domain-specific interpretation; archetype-based rules and verification; Semantic Closure. Must work without AI agents.
- **L2 Agent-Native Development**: agents interact with software through its executable semantic model. They discover relevant Loci, purpose/responsibilities, relationships/dependencies, available operations, contracts, applicable rules, available verification procedures, missing information, permitted actions. Eventually investigate, propose, implement, verify, evolve changes through these interfaces; may request more knowledge/scope/authority. **Primary strategic reason for Telos.**
- **L3 Frameworks and Applications**: existing tech (React, TanStack, Effect, Bun, REST, databases, AI agents, infra, requirements systems, testing libs) incorporated via specialized semantic extensions. No mandatory application architecture. Telos provides the common semantic foundation, not application-specific behavior.

## 2. The fundamental concept: Locus
**Locus is the only fundamental semantic entity.** An identifiable semantic context responsible for some part of a software system; foundation for meaning, ownership, properties, relationships, capabilities. Not necessarily a file/module/class/runtime actor/service/graph node/executable component — but can represent any when appropriate. Universal Locus stays minimal: NO mandatory fields for every domain. Do not require every Locus to have a Charter, agent config, tests, metrics, infra config, or a fixed set of operation types.

Composable semantic extensions specialize a Locus (illustrative, not required API):
```typescript
const AgenticLocus = Locus.extend(AgentSemantics)
const WebAgentLocus = AgenticLocus.extend(WebSemantics, MetricsSemantics, TestSemantics)
```
An extension can introduce: typed properties, relationship types, additional contracts, semantic interpretations, verification rules, domain-specific operations, adapters to existing libraries, new agent-discoverable capabilities. Composition yields a more specialized Locus. Extensions independently definable and reusable. Composition must DETECT incompatible definitions rather than silently overwriting. **No separate fundamental Node, Fabric, Component, Resource, or Agent entity systems.** An application can be a root Locus; a component a specialized Locus; an agent a Locus with agent semantics; reusable definitions an ordinary package. No unnecessary foundational entity types.

## 3. Nature of semantics
**A graph is not semantics; a graph is one possible representation of semantic relationships.** Semantics describes meaning of entities, properties, relationships, operations, contracts, constraints, implementation bindings. Must support general semantic relationships and domain-specific semantics from extensions. E.g.: one Locus owns an implementation; another invokes its operation; an agent exposes it as a tool; a CLI command maps args to it; a React component uses its result; an Archetype defines valid interactions. These have different meanings; untyped edges are inadequate. Developers must be able to define new semantics without changing the universal Locus implementation.

**Semantic Closure — "No Code Outside Semantics"**: every framework-managed code artifact belongs to an identifiable semantic context. Not every function needs its own Locus; functions/components/tests may belong to larger Loci, but ownership must be discoverable. Important cross-boundary dependencies represented or explicitly reported as unknown. System must detect code outside declared ownership coverage. Start practical, document limitations. Do NOT claim complete coverage of arbitrary JS execution when analysis only covers modules/files. Third-party libs represented via external semantic boundaries without modeling internals.

## 4. Archetypes and specialized verification
**No universal algorithm proving correctness of arbitrary software.** Telos provides a universal mechanism for composing, interpreting, applying semantics; specialized verification comes from **Archetypes** (rules for particular semantic contexts). Examples: CLI conventions, React component architecture, REST API contracts, agent tool definitions, arithmetic behavior, Effect service composition, React↔REST relations, CLI/Web/Agent-tooling relations. An Archetype may introduce allowed relationships, required contracts, architectural constraints, domain validation, static analysis rules, test strategies, verification procedures, external analysis adapters. May be represented as specialized Loci if coherent/composable; don't force if it creates circular abstraction. The Semantic Kernel determines which rules apply to a semantic composition and invokes their checkers. Different Archetypes may use entirely different verification mechanisms. **Declared meaning, verified behavior, observed behavior must remain distinguishable. An unverified claim must not silently become a guarantee.**

## 5. Single source of truth — Code is the source of truth
Canonical semantic definitions live in executable TypeScript. Docs, diagrams, agent context, indexes, projections, tool schemas, verification plans are DERIVED from or programmatically linked to them. No parallel manually maintained semantic models. ADRs/specs record intent, decisions, rationale; runtime observations/tests are evidence; neither silently redefines canonical semantics. Eventually distinguish: declared, derived, verified, observed, unknown, invalidated knowledge. An agent's memory/summary is not authoritative.

## 6. Agent-native access is a core requirement
First semantic APIs designed for programmatic discovery. Agent resolves a Locus and inspects it without opening implementation files. Conceptual:
```typescript
const locus = yield* telos.resolve("calculator")
const description = yield* locus.inspect()
const relations = yield* locus.relations()
const capabilities = yield* locus.capabilities()
const verification = yield* locus.verifications()
```
Design real APIs from TypeScript, Effect and the existing repo. Operations must expose genuine structured semantic information from the same model the software uses. Agent tool definitions are DERIVABLE from semantic capabilities; no manual duplication of operation contracts in unrelated agent schemas. Information access ≠ modification authority: discovering a relationship does not authorize modifying the referenced Locus. Full runtime isolation, authority delegation, autonomous evolution are future, but initial architecture must not make them impossible. Not docs-only: agents must be able to query and operate through it.

## 7. Packs and existing technologies
A Pack is a prepared reusable distribution of semantic definitions/integrations (Locus definitions, extensions, Archetypes, adapters, implementations, verification tools, examples). Not necessarily a distinct runtime entity; can be an ordinary TS package. Developers can replace/extend/combine. Telos must not require replacing React, Effect, PostgreSQL, Vitest etc.; it describes and governs their use via semantic extensions.

## 8. Technology

Don't rebuild what Effect provides. No Rust, custom language, or graph DB without demonstrated need. Use installed tool versions and workflows.

## 11. Required working proof: Calculator
After the minimal foundation, demonstrate through one calculator exposing the same arithmetic (add, subtract, multiply, divide) via three interfaces: 1) CLI 2) Web 3) Agent Tools. One actual arithmetic implementation, shared contracts, consistent error handling. CLI/Web/Agent integrations semantically independent and composable; may use existing libs. Web: use existing documentation app if suitable, else TanStack Start + React + shadcn/ui + Bun. Agent Tooling: prefer suitable capabilities from the installed Effect ecosystem. A deterministic agent-compatible test client must discover and invoke the tool without external LLM API credentials.

Must demonstrate (not merely that three interfaces call one function): **Semantic ownership** (source and managed artifacts have identifiable Locus owners); **Semantic composition** (arithmetic, CLI, Web, Agent semantics independently definable and composable); **Executable introspection** (structure queryable programmatically); **Capability discovery** (agent-compatible client discovers operations and contracts); **Archetype verification** (Archetypes validate local and cross-Locus constraints); **Semantic relationships** (model identifies CLI, Web, Agent depend on/expose the same arithmetic capability); **Change impact** (if the shared arithmetic contract changes, Telos discovers affected relationships and applicable checks — using the real semantic model, NOT hardcoded consumer lists).
